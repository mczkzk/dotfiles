# Visual Report

文章で説明して伝わらなかったことを、**実物の画面と数字と図**で 1 枚の HTML にまとめる。
読み手は、その話題を初めて見る人だと思って書く。

このスキルが要るのは「分かっている人が書いた正しい文章」が通じなかった場面である。
そういうとき文章を足しても通じない。読み手に足りていないのは言葉ではなく、頭の中の絵のほうだ。

## 進め方

### 1. 誰が、何を分かっていないのかを決める

書き始める前に、次の 3 つを 1 行ずつ言えるようにする。言えないなら、まだ材料が足りない。

- **読み手**。ユーザー本人か、PM か、レビュアーか。その人が既に知っていることと知らないこと
- **読み手の問い**。ユーザーが実際に言った言葉をそのまま使う (例「これは何のためのボタン？」「なぜ押せないの？」)。題名はこの問いにする
- **読み終わったあとに、読み手ができるようになること**。理解するだけか、何かを決めるのか

読み手が違えば別のファイルにする。本人向けの資料に入っている内輪の話 (自分の説明の訂正、計測用の細工、内部の ID) は、他人向けには載せない。
逆に、決めてもらうための資料には「何を決めてほしいか」と選択肢を最後に入れる。

### 2. 言うことを先に確かめる

レポートは見た目が整うぶん、中身が本当らしく見える。だから**確かめていないことを載せない**。

- 原因や仕組みを説明するなら、推測ではなく実際に動かして数える。途中の段階ごとに「いくつ残ったか」を記録すると、どこで起きているかが分かる
- 数字は測った値を書く。画像から読み取った値や計算上の目安は、そうと分かるように書くか、測り直す
- 「確かめていないこと」の節を作るくらいなら、確かめてから書く。確かめられないものだけ、1 行で残す
- 1 つの例だけで言い切らない。別の条件 (別のデータ、別の設定) でも同じになるかを見る

途中で自分の前の説明が間違いだったと分かったら、隠さずに直す。本人向けには何をどう間違えたかを書く。他人向けには正しい内容だけを書く。

### 3. 材料を集める

絵の種類ごとに役割が違う。全部を使う必要は無いが、**実物を最低 1 つ**入れる。

| 種類 | 何のために使うか | 作り方 |
|---|---|---|
| 実物の画面 | 「アプリのどこの話か」を一目で伝える | ブラウザ操作で撮る。プロジェクトに `/e2e-verify` や撮影の手順があればそれに従う |
| 同じ場所の比較 | 「何が変わるか」を伝える。これがいちばん効く | 条件だけを変えて、同じ範囲、同じ縮尺で 2 枚撮る |
| 内部データの絵 | 画面には出ない途中の状態を見せる | ページ内で canvas に描いて撮る。色の意味をキャプションに書く |
| 模式図 | 仕組みを単純化して見せる | inline SVG。**必ず「模式図」と書く** (実データと混ぜると嘘になる) |
| 動画 | 時間の経過 (固まる、順番に動く) を見せる | `/e2e-record`。HTML には `<video controls>` で入れる |
| 表 | 数字の比較 | 行は少なく。結論の行に色を付ける |

撮るときの注意。

- 画面全体は情報が多すぎる。見せたい部分を切り出す (`ffmpeg -i in.png -vf crop=W:H:X:Y out.png`)。小さい部分は拡大する (`scale=...:flags=neighbor` でぼかさない)
- 比較の 2 枚は、切り出す範囲と倍率を必ずそろえる
- 撮影のためにコードや設定を一時的に変えたら、終わったら戻して `git status` で確かめる
- 画像は読み手に渡す資料と同じフォルダの下に置く (相対パスで参照するため)。リポジトリを汚さない場所を選ぶ (タスク用のフォルダなど)

### 4. 書く

`assets/template.html` を出発点にする。見た目は既に整っているので、中身に集中する。

構成の型。

1. **それは何か**。読み手の勘違いを最初に解く。実物の画面を 1 枚
2. **ふつうはどう動くか**。手順ごとに画像と数字
3. **問題の条件では何が起きるか**。同じ場所の比較と、なぜそうなるかの模式図
4. **だから何が言えるか**。箇条書きで 3 つまで。決めてほしいことがあれば選択肢

書き方。

- **節の最初に結論を 1 文**で書く (`.oneline`)。そこだけ拾い読みしても話が通じるようにする
- 1 つの節で言うことは 1 つ
- 画像には必ずキャプションを付け、「どこを見ればよいか」を言う (例「赤い枠の中が、押せなくなったボタン」)。画像を置いただけでは、読み手は何を見ればよいか分からない
- 専門用語は初めて出るところで言い換える。コードの関数名やファイル名は、開発者向けでなければ出さない
- 数字は表に、理由は文に。表の列は読み手が違いを言える名前にする (2 つの列の違いが説明できないなら 1 つにまとめる)
- 読み手に関係ない文は消す。ユーザーとの会話でだけ意味があった文 (質問への直接の返事など) は、他人向けには要らない
- 長さは「短いほどよい」ではなく「読み手が迷わない」で決める。図が多くて長いのは構わない。文が多くて長いのは削る

### 5. 表示を確かめる

書いただけで渡さない。自分で開いて見る。

- 参照している画像が全部あるか (`grep -o 'src="[^"]*"'` で拾って存在を確かめる)
- 実際の見え方。Playwright MCP は `file://` を開けないことがあるので、そのフォルダで一時的に `python3 -m http.server <port> --bind 127.0.0.1` を立てて開き、全体のスクリーンショットを見る。終わったら止める
- 図の文字が重なっていないか、表が崩れていないか、画像が大きすぎないか

### 6. PDF にする (頼まれたとき、または添付して送るとき)

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --no-pdf-header-footer --print-to-pdf="$PWD/report.pdf" "file://$PWD/report.html"
```

- テンプレートには印刷用の指定が入っている (図や表をページの途中で切らない、画像を小さめにする、背景色を出す)
- できた PDF を Read で開いて、全ページを見る。空白だらけのページや、1 行だけ次のページに流れた箇所があれば、画像の高さを調整して作り直す
- HTML を直したら PDF も作り直す。作り直したら、変えたページをもう一度見る

### 7. 渡す

- ファイルの絶対パスを伝える
- 何が実測で、何が模式図か。確かめていないことが残っていれば、それも言う
- 外に出す資料 (JIRA、Slack、PR) は、勝手に投稿しない。置き場所を伝えて止める

## よくある失敗

- **文章のレポートを作ってしまう**。見出しと箇条書きだけの HTML は、元の説明と変わらない。画面か図が無い節があったら、その節は絵にできないか考える
- **確かめる前に図を作る**。きれいな図に間違った説明が載ると、直すのに 2 倍かかる
- **模式図を実データのように見せる**。読み手は図の数字を信じる
- **1 枚に全部の読み手を詰め込む**。本人向けと他人向けは分ける
- **渡したあとで読み手の言葉とずれる**。読み手が「よけいじゃね？」「ちがいがわからん」と言ったら、その文や列は読み手の役に立っていない。説明を足さずに削るか、まとめる
